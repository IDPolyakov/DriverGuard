	# Полное описание проекта

## Название

**DriverGuard CLI — интеллектуальная система мониторинга состояния водителя на C++**

Система в реальном времени получает изображение с камеры, отслеживает лицо водителя, положение головы, состояние глаз и рта, оценивает признаки усталости и невнимательности, после чего при помощи **нечёткой логики** определяет уровень риска и выбирает подходящую реакцию.

Основная идея проекта — не просто определить:

```
глаза закрыты → подать сигнал
```

а объединить несколько слабых признаков:

```
глаза закрываются чаще
+
водитель начал зевать
+
голова периодически опускается
+
взгляд долго направлен вниз
```

и получить итоговую оценку:

```
Усталость: высокая
Невнимательность: средняя
Риск: 78%
```

После этого система самостоятельно решает, какое предупреждение использовать:

```
ничего
↓
текстовое сообщение
↓
короткий звуковой сигнал
↓
голосовое предупреждение
↓
повторяющееся критическое предупреждение
```

Это хорошо соответствует требованиям задания: должны быть реализованы фаззификация данных, база правил и нечёткий логический вывод. НМУ и ИИФ.pdfPDF

# 1. Получение видео

Используется камера ноутбука или USB-камера.

За это отвечает OpenCV:

```
cv::VideoCapture camera(0);
```

На каждом шаге программа получает кадр:

```
Camera
 ↓
Frame
 ↓
Processing
```

Например, работа идёт с частотой 20–30 FPS.

Само изображение можно уменьшать перед обработкой, чтобы система работала быстрее.

Например:

```
камера:     1920×1080
анализ:      640×360
вывод:      1280×720
```

---

# 2. Обнаружение лица

На каждом кадре система должна найти лицо пользователя.

Получаем:

```
┌──────────────────────────┐
│                          │
│       ┌─────────┐        │
│       │  FACE   │        │
│       │   🙂    │        │
│       └─────────┘        │
│                          │
└──────────────────────────┘
```

После этого дальнейший анализ выполняется только внутри области лица.

Это позволит определить:

- глаза;
- рот;
- нос;
- подбородок;
- ключевые точки лица.

# 3. Facial landmarks

Одного OpenCV для качественных landmarks лица может быть недостаточно удобно, поэтому здесь разумно подключить дополнительную модель.

Она должна выдавать точки вроде:

```
левый глаз
правый глаз
нос
углы рта
верхняя губа
нижняя губа
контур лица
```

Из этих точек уже можно вычислять почти всё остальное.

# 4. Анализ глаз

Для каждого глаза определяются координаты нескольких точек.

После этого рассчитывается показатель открытости глаза, например EAR.

Условно:

```
EAR = 0.31 → глаз открыт
EAR = 0.25 → частично закрыт
EAR = 0.18 → закрыт
```

Но поскольку у нас используется нечёткая логика, жёсткий порог нам не особенно нужен.

Можно определить классы:

```
OPEN
HALF_CLOSED
CLOSED
```

И получить:

```
EAR = 0.23

OPEN        = 0.15
HALF_CLOSED = 0.82
CLOSED      = 0.31
```

То есть одно значение может частично принадлежать нескольким состояниям.

Именно это и есть фаззификация.

# 5. Моргание

Программа хранит историю EAR.

Например:

```
0.31
0.30
0.28
0.18
0.15
0.17
0.27
0.31
```

Она видит:

```
открыт
↓
закрылся
↓
открылся
```

Значит произошло моргание.

После этого можно считать:

```
blink count
blink frequency
average blink duration
maximum blink duration
```

Например:

```
Blinks/min:     17
Average blink:  190 ms
Longest blink:  430 ms
```

---

# 6. Долгое закрытие глаз

Это один из главных признаков.

Обычное моргание система не должна считать опасностью.

Поэтому отдельно измеряется:

```
eyeClosedDuration
```

Например:

```
120 ms → NORMAL
350 ms → SUSPICIOUS
700 ms → DROWSY
1500 ms → CRITICAL
```

Но снова используем нечёткие категории:

```
SHORT
MEDIUM
LONG
VERY_LONG
```

---

# 7. PERCLOS

Система хранит информацию о состоянии глаз в некотором временном окне.

Например:

```
последние 60 секунд
```

И вычисляет долю времени, когда глаза были закрыты.

```
PERCLOS =
timeEyesClosed / observationTime
```

Например:

```
Observation: 60 sec
Eyes closed: 13 sec

PERCLOS = 21.6%
```

Это будет одним из важных входных параметров fuzzy-системы.

---

# 8. Анализ рта и зевоты

По landmarks рта можно получить показатель его открытости.

Условно:

```
MAR — Mouth Aspect Ratio
```

Система отслеживает:

```
рот закрыт
рот открыт
рот широко открыт
```

Но просто открытый рот не считается зевком.

Нужно учитывать время:

```
mouth openness
+
mouth open duration
```

Например:

```
IF mouth_open = HIGH
AND duration = LONG
THEN yawn = HIGH
```

Дальше считается:

```
Yawns last 5 min: 4
```

# 9. Положение головы

Очень полезная часть проекта.

Используются точки:

- нос;
- подбородок;
- глаза;
- уголки рта.

На основании их положения OpenCV может приблизительно определить ориентацию головы.

Получаем три угла:

```
Yaw
Pitch
Roll
```

### Yaw

Поворот:

```
← влево

   🙂

вправо →
```

### Pitch

```
вверх
  ↑
 🙂
  ↓
вниз
```

### Roll

Наклон головы:

```
🙂
 ↘
```

Например:

```
Yaw:    32°
Pitch: -18°
Roll:    4°
```

# 10. Определение отвлечённости

Положение головы можно использовать для оценки внимания.

Например:

```
Yaw ≈ 0
Pitch ≈ 0

→ человек смотрит вперед
```

Но:

```
Yaw = 45°
Duration = 4 sec
```

может означать, что водитель долго смотрит в сторону.

Или:

```
Pitch = -30°
```

может означать взгляд вниз.

Вводится параметр:

```
LookingAwayDuration
```

Например:

```
0.2 sec
0.8 sec
2 sec
5 sec
```

# 11. Направление взгляда

Это можно сделать как расширенную часть проекта.

Система анализирует глаза и приблизительно определяет направление:

```
LEFT
RIGHT
CENTER
DOWN
UP
```

Тогда можно отличать:

```
голова вперед + глаза вправо
```

от:

```
голова полностью повернута вправо
```

Для первого MVP это можно не делать.

Сначала достаточно положения головы.

# Нечёткая логика

Это будет центральная интеллектуальная часть проекта.

Я бы сделал минимум три системы.

## Fatigue Fuzzy Engine

Входы:

```
PERCLOS
EyeClosedDuration
BlinkDuration
YawnFrequency
HeadNodFrequency
```

Выход:

```
FatigueLevel
```

Состояния:

```
LOW
MEDIUM
HIGH
CRITICAL
```

---

## Attention Fuzzy Engine

Входы:

```
HeadYaw
HeadPitch
LookingAwayDuration
```

В дальнейшем:

```
GazeDirection
```

Выход:

```
AttentionLevel
```

Например:

```
FOCUSED
REDUCED
DISTRACTED
CRITICAL
```

---

# Risk Fuzzy Engine

Это второй уровень.

Он берёт уже рассчитанные:

```
Fatigue
Attention
```

а также дополнительные параметры:

```
TripDuration
NumberOfRecentWarnings
WarningIgnoredCount
```

И определяет:

```
RiskLevel
```

Например:

```
SAFE
LOW
MEDIUM
HIGH
CRITICAL
```

---

# Пример работы правил

Например:

```
IF PERCLOS HIGH
AND yawnFrequency HIGH
THEN fatigue CRITICAL
```

Другой вариант:

```
IF eyeClosedDuration LONG
AND headPitch DOWN
THEN fatigue HIGH
```

Или:

```
IF lookingAwayDuration LONG
AND headYaw LARGE
THEN attention LOW
```

После этого:

```
IF fatigue HIGH
AND attention LOW
THEN risk CRITICAL
```

# Как технически устроить голосовой ввод

Нужны три части:

```
Microphone
   ↓
Audio Capture
   ↓
Speech-to-Text
   ↓
Command Parser
```

Например пользователь говорит:

```
"покажи статус"
```

Speech Recognition возвращает строку:

```
покажи статус
```

Дальше твоя программа уже обычным C++ кодом распознаёт команду:

```
покажи статус
    ↓
Command::STATUS
```

И выполняет её.

# Калибровка пользователя

При первом запуске:

```
No calibration profile found.

Start calibration? [Y/n]
```

Потом программа говорит:

```
Look straight into the camera.
```

Собирает несколько секунд данных.

Затем:

```
Blink normally several times.
```

После:

```
Look left.
Look right.
Look down.
```

И формирует baseline.

Например:

```
Normal EAR:       0.287
Closed EAR:       0.171

Normal head yaw:   1.7°
Normal pitch:     -2.1°
```

Это сильно улучшает проект, потому что система становится персонализированной.

# Адаптивность

Помимо физиологических параметров, программа может запоминать реакцию пользователя на предупреждения.

Например:

```
WARNING
↓
водитель посмотрел вперед через 0.6 sec
```

значит предупреждение сработало.

Но:

```
WARNING
↓
состояние не меняется 8 sec
```

значит его проигнорировали.

Система ведёт:

```
audioResponseScore
voiceResponseScore
visualResponseScore
```

И со временем выбирает предпочтительный тип предупреждения.

Например:

```
IF audioResponse HIGH
AND visualResponse LOW
THEN preferredAlert AUDIO
```

Это очень хорошо соответствует требованию адаптации интерфейса под пользователя. НМУ и ИИФ.pdfPDF

# Почему whisper.cpp

Для твоего проекта это очень подходящий вариант.

Он:

- написан под C/C++;
- работает локально;
- не требует внешнего облачного API;
- можно использовать из C++;
- хорошо подходит для небольшого набора голосовых команд.

Архитектура:

```
Microphone
  ↓
PCM audio
  ↓
whisper.cpp
  ↓
"покажи статус"
  ↓
CommandParser
  ↓
STATUS
```

Для начала можно вообще не делать continuous recognition.

Например пользователь нажимает:

```
V
```

и программа пишет:

```
Listening...
```

Записывает 3–5 секунд голоса.

Распознаёт.

Это **значительно проще**, чем постоянно слушать микрофон.

# 3. Как работает адаптивность

Вот здесь уже интереснее.

Система должна не просто всегда одинаково пищать.

Она должна учитывать, **какой способ взаимодействия лучше подходит конкретному пользователю**.

По сути ты создаёшь профиль водителя.

Например:

```
struct DriverProfile {
    double visualAlertPreference;
    double audioAlertPreference;
    double voiceAlertPreference;

    double warningSensitivity;

    double baselineEAR;
    double normalHeadPitch;
    double normalHeadYaw;
};
```

То есть адаптивность можно сделать на двух уровнях.

## Адаптация №1 — под физиологию человека

У разных людей разные глаза, форма лица, нормальный наклон головы.

Поэтому при первом запуске проводится калибровка.

Система говорит:

> «Смотрите прямо в камеру.»

Потом:

> «Моргните несколько раз.»

Потом:

> «Посмотрите влево.»

> «Посмотрите вправо.»

Система получает нормальные значения именно этого водителя:

```
Normal EAR = 0.29

Normal head yaw = 2°
Normal head pitch = -4°
```

Для другого человека:

```
Normal EAR = 0.24

Normal head yaw = -3°
Normal head pitch = 1°
```

Получается, система не использует один универсальный порог для всех.

Это уже адаптация.

# 4. Но для задания лучше добавить ещё адаптацию интерфейса

Потому что преподаватель может сказать:

> Это адаптация алгоритма, а где адаптация интерфейса?

И здесь мы делаем ещё один слой.

Система отслеживает, на какие предупреждения пользователь лучше реагирует.

Например ситуация:

```
водитель отвлёкся
↓
появилось визуальное предупреждение
↓
5 секунд нет реакции
```

Запоминаем:

```
visual alert response = poor
```

В следующий раз:

```
визуальное предупреждение
+
beep
```

Если после beep водитель сразу посмотрел вперёд:

```
audio alert response = good
```

После нескольких поездок профиль может выглядеть так:

```
Visual warnings: 0.35
Sound warnings:  0.91
Voice warnings:  0.76
```

То есть система понимает:

> Этот пользователь лучше всего реагирует на звук.

И дальше начинает раньше использовать звуковой канал.

# 5. Пример реальной адаптации

В начале у всех стандартное поведение:

```
Risk LOW
→ ничего

Risk MEDIUM
→ текст + изображение

Risk HIGH
→ beep

Risk CRITICAL
→ beep + voice
```

После нескольких поездок для водителя A:

```
Visual response: HIGH
Audio response: MEDIUM
Voice response: LOW
```

Система адаптируется:

```
MEDIUM
→ крупное визуальное предупреждение

HIGH
→ визуальное + beep

CRITICAL
→ визуальное + beep
```

Голос используется редко.

А для водителя B:

```
Visual response: LOW
Audio response: HIGH
Voice response: VERY_HIGH
```

Будет:

```
MEDIUM
→ beep

HIGH
→ voice warning

CRITICAL
→ loud beep + repeated voice warning
```

Вот это уже очень сильная демонстрация адаптивного интерфейса.

# 7. Адаптация через fuzzy logic

И я бы специально сделал выбор интерфейса тоже через нечёткую логику.

Например входы:

```
visual_response
audio_response
voice_response
risk_level
previous_warning_ignored
```

Выход:

```
alert_mode
```

Функции принадлежности:

```
visual_response:
LOW
MEDIUM
HIGH

audio_response:
LOW
MEDIUM
HIGH

risk:
LOW
MEDIUM
HIGH
CRITICAL
```

Правила:

```
IF
    visual_response LOW
AND audio_response HIGH
THEN
    preferred_alert AUDIO
```

```
IF
    risk HIGH
AND voice_response HIGH
THEN
    preferred_alert VOICE
```

```
IF
    previous_warning_ignored HIGH
THEN
    alert_intensity INCREASE
```

```
IF
    risk CRITICAL
THEN
    alert_mode MULTIMODAL
```

Последнее означает:

```
текст
+
изображение
+
звук
+
голос
```

одновременно.

Это вообще идеально закрывает требование проекта, потому что в исходном задании прямо говорится, что адаптивность и форма предоставления результата могут определяться нечётким выводом. На второй странице примера предлагается учитывать историю взаимодействия и выбирать предпочтительный вариант взаимодействия с пользователем. НМУ и ИИФ.pdfPDF НМУ и ИИФ.pdfPDF

# 10. Как это сформулировать в документации

Можешь практически использовать такую формулировку:

> **Мультимодальность интерфейса** реализуется за счёт нескольких способов взаимодействия пользователя с системой. Текстовый ввод осуществляется посредством командного интерфейса CLI, а голосовой ввод — посредством подсистемы распознавания речи. Результаты работы системы предоставляются в текстовой форме через консоль, в графической форме через окно OpenCV с отображением видеопотока и результатов анализа, а также в аудиоформе посредством звуковых и голосовых предупреждений.

А про адаптивность:

> **Адаптивность интерфейса** заключается в персонализации способов представления информации и предупреждений. Система хранит профиль пользователя, учитывает его физиологические параметры, историю взаимодействия и реакцию на различные виды уведомлений. На основании этих данных система нечёткого вывода определяет предпочтительный способ взаимодействия: текстовый, визуальный, звуковой или голосовой, а также регулирует интенсивность и уровень детализации предупреждений.

Вот в таком виде твой проект очень хорошо укладывается в формулировку задания.
